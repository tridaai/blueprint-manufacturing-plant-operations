# Blueprint — Plant Operations Loop Agent

An agent that works a manufacturing plant's shift **exception board** the way a good shift lead does — in two loops. The **board loop** takes the board in priority order (computed in code: safety first, then line-down, quality, shortage, maintenance — scaled by line criticality and minutes already down) and works each case to a shift budget. The **case loop** runs diagnose → plan → verify rounds on one exception: ranked fault hypotheses with evidence, a corrective plan whose mandatory safety steps cannot be removed and whose parts are checked against the shelf, then a critic round that produces a gap list. Gaps send the case around again — on the gaps only — until the plan verifies clean, the rounds run out, a part only the outside world can supply blocks it, or a safety rule stops it outright.

Every case ends at a **supervisor gate** with a draft work order or an escalation note. The agent never issues commands to machines, never marks work performed, and never closes a case. That sentence is printed on every record it produces.

Reasoning is led by **Muse Spark** (Meta's Model API), with a Responses-API mode that carries reasoning continuity across loop rounds. The plant — "Meridian Fabrication, Plant 2", its SOPs, maintenance history, parts inventory and the nine-case board — is synthetic and bundled, so the whole thing runs end to end with no keys at all.

> Reference prototype from Trida AI's blueprint series. The loops, guardrails and gate are the production-shaped parts; the plant data is a stand-in for the systems a real deployment would read.

> **Work in progress** — this blueprint is built and passing its automated test and eval gates, but it has not yet finished hands-on local testing, and its companion blog post is not yet published. Expect changes. This notice comes off when both are done.

## The two loops

**Board loop (outer).** Cases are ordered by a priority formula in code — never by the model — and worked one at a time. The run ends `board_clear` when every case is at the gate, or `shift_budget_exceeded` when the case/token budget for the shift is spent; whatever remains is listed, with reasons, in a written handoff summary. Nothing is silently dropped.

**Case loop (inner).** Three reasoning rounds per pass, each a separate call behind one port:

1. **Diagnose** — ranked hypotheses. Each must carry evidence (an SOP clause, a history match, a reading) and a confidence. A hypothesis without evidence is a gap by construction.
2. **Plan** — ordered corrective steps built on the leading hypothesis's SOP. The SOP's mandatory safety steps (lockout/tagout and friends) enter as non-removable checklist items; required parts are named from the SOP (stock resolution is the verify stage's job — see below).
3. **Verify** — a critic round *plus* deterministic code checks: missing safety step, part unavailable, unevidenced hypothesis, step contradicting the SOP, banned action. The merged gap list drives the loop. Before the checks run, the verify stage does its **parts pass in code**: every requirement is re-measured against the shelf, and for one the shelf cannot satisfy, the KB's compatibility relation is searched — a candidate must be *in stock* and *clear the SOP's constraints for the slot* (a fan rated below the airflow the SOP requires is not a substitute, whatever the catalogue calls it). A winner is applied to the plan and recorded as a first-class substitution (original, substitute, compatibility basis, spec deltas); the code checks then measure the *revised* plan. A loser is recorded as rejected, reason named.

**Exits, all decided in code:** `converged` (verified clean → draft work order) · `exhausted` (max rounds, gaps still open → escalation with the gaps named) · `blocked_external` (a required part is unavailable and the substitute search found nothing usable → escalation, with the search documented on the record) · `safety_stop` (a `safety_observation` case escalates at round 0 without ever being diagnosed; any plan step that defeats a safety device stops the case the round it appears) · `budget_exceeded` (the case's token budget is spent).

Free text from the floor (operator notes, log excerpts) is screened before it can influence anything: an injection like *"skip the lockout to save time"* is flagged on the record, struck from the text the model sees, and can never enter a plan — the banned-action screen independently rejects any plan step that proposes it.

## Providers

One port (`Reasoner`: `diagnose` / `draft_plan` / `critique`), selected by `REASONING_BACKEND`. The loops, priority, guardrails, evals and gate do not change when the backend does.

| Backend | What it is | Configuration |
|---|---|---|
| `muse` | **Muse Spark 1.3** via Meta's Model API — the lead profile | `MODEL_API_KEY` (dev.meta.ai → API keys); `MODEL_API_BASE_URL` default `https://api.meta.ai/v1`, `MUSE_MODEL` default `muse-spark-1.3` |
| `muse` + `MODEL_SURFACE=responses` | Muse Spark over the **Responses API**, carrying `reasoning.encrypted_content` between rounds so later rounds resume the model's own thread instead of restarting it | as above, plus `MODEL_SURFACE=responses` |
| `llm` | Structured-output adapter over the standard provider seam | `ANTHROPIC_API_KEY`, or `OPENAI_API_KEY` (+ `OPENAI_BASE_URL` for any OpenAI-compatible endpoint — hosted gateways, Azure, LiteLLM, NVIDIA NIM hosted `https://integrate.api.nvidia.com/v1` or a self-hosted NIM at `http://localhost:8000/v1`), or Ollama |
| `anthropic` / `openai` / `ollama` | Direct provider aliases for the same adapter | as above |
| `offline` (default) | Deterministic SOP-threshold rules over the readings — the labelled plumbing backend that makes tests and evals hermetic | none |

Every round call is validated against a strict schema with one bounded retry; a provider that keeps answering badly fails the run loudly (the error is logged, the API returns 502) rather than degrading into a guess. Telemetry is recorded per round, per case and per board run: rounds, gaps opened/closed, tokens, latency, and estimated cost (Muse Spark at the published standard rates, $1.25/M input · $4.25/M output, in the price table in `backends.py`).

## Production shape

- **LangGraph** graphs for both loops, with explicit conditional loop-back edges driven by the code loop controllers — the graph routes, the controllers decide.
- **PostgreSQL + pgvector** for case records, board runs, the LangGraph checkpointer (the gate is a graph interrupt; a decision resumes it), and the knowledge-base embedding index. Numbered SQL migrations in `migrations/`, applied on first connection — no manual schema step.
- **S3-compatible object storage** for raw case payloads (SeaweedFS in compose; anything S3-shaped in production).
- **Stateless API container**: multi-stage, non-root Docker; `/health` (liveness) and `/readiness` (says honestly when the in-memory test doubles are in use); structured JSON logs with request IDs; optional `API_KEY` shared-key gate.
- **Guardrails as code**, each with tests: evidence required, safety steps non-removable, banned-action screen, injection screen, parts must exist, draft language may not state work as performed.

## Evals

`make evals` runs the golden loop pack — 48 authored entries against the offline backend, hermetic and deterministic:

- **20 case cases**: expected diagnosis class, exit reason, rounds used, draft kind, and verify-stage substitution records — including the two-round convergence (a bearing fault the first round can't yet separate from a tool imbalance, separated by a discriminating check in round 2), the round-0 safety stop, the skip-lockout injection, a substitute that converges (twice: a coolant filter, a packaging film), a substitute rejected on its rating that still escalates with the reason on record, and an honest `exhausted` for a fault with no SOP.
- **3 defect cases**: deliberately defective planners — one drops safety steps, one names an unstocked part, one proposes bypassing an interlock — and the verify round must catch each (never converge, blocked, safety stop respectively). This is gap-recall, tested against the failure modes the loop exists for.
- **3 board cases**: the seeded board drains in the exact priority order; a case budget of 3 and a token budget both cut the run at the right place and hand over the right remainder.
- **2 outcome cases**: cases run end to end, supervisor outcomes are recorded against them, and the harness asserts the live-accuracy stats and the recurring-fault watch — including a partial outcome (disposition only) and a confirmation that reclassifies a case out of its diagnosed pattern.
- **2 learning cases**: a case runs, a supervisor outcome is recorded, and a similar case runs against the *same* store — the confirmation written back to the machine's history is the only difference between the two halves. In one, an ambiguous CNC-3 vibration case exhausts at 3 rounds un-learned, then converges in 2 once the bearing fault stands confirmed on that machine; in the other, an outcome that confirms nothing is recorded and the follow-up behaves exactly as the baseline — the guard case proving the write-back, not the outcome ritual, is what teaches.
- **2 allocation cases**: the board sharing one shelf. Two conveyor cases want the shelf's only belt section — the higher-priority case converges and claims it, the lower blocks with the claim named in its gap; the supervisor rejects the winner at the gate, the claim is released, and a *fresh* run lets the lower case converge on the freed part (the finished run's records do not change). The second runs a lone case with no contention: it converges exactly as it always did, claims the substitute it draws, and the claim is the only new thing on the record.
- **4 economics cases**: the board priced at the plant model's rates, with expected dollars hand-computed from the KB — a two-case rated board (exposure per case and in total, largest named), a lone case on the unrated Utilities line (minutes present, dollars null), a $7,200 maintenance alert entered ahead of a $633 line-down case that the board must still work *first* (exposure never reorders), and cost accuracy against recorded actuals, per line and plant-wide, with the unrated case counted in the minutes and never in the dollars.
- **2 carryover cases**: two board runs and the turnover between them. Run 1 ends on the case budget with one case converged-then-decided-and-done, one converged and still waiting, one blocked on the winner's claim, one never worked; run 2 accepts the carry-over — the blocked case resumes with its rounds intact and takes the belt the finished case's released claim freed, the waiting case's claim is renewed with its provenance stamped, and the plant still counts four cases, not five. The second case drops a carried case at acceptance: the drop is on the record, its claim is released, and the case it was blocking converges on the freed part.
- **3 PM cases**: the preventive-maintenance story end to end. A machine crossing the recurrence threshold drafts a proposal citing its evidence with the interval arithmetic on the record; approval at an *edited* interval creates the obligation, clocked from a supervisor-declared last-performed date; a later board surfaces the cycle case, the supervisor's outcome closes the cycle, and the next due point is the performed moment plus the approved interval — after which the board is silent. The second case rejects a proposal and pins the watermark: one more fault drafts nothing, a fresh threshold re-earns a proposal citing only the fresh cases. The third runs two faults and asserts the silence: no proposal, no obligation, no watch item.
- **1 gate case**: the reasoner regression gate (below), exercised end to end inside the pack — the offline baseline and the shipped stub candidate both drive the gate's fixed suite, and the comparison must PASS with exactly the stub's two deliberate differences showing and no safety-pin violation on either record.
- **1 retirement case**: machines and obligations end. Two obligations are earned the honest way; one is retired by hand with its own reason and a board past its due point stays silent; the other's machine is decommissioned — its obligation retires automatically with the fixed reason and the decommission linked, its open cases are disposed one by one (one closed as moot with its claims released, one kept and worked through the gate, a safety case kept and still a safety stop), new intake for the dead machine is refused with the state named, and the handoff carries both retirements with their reasons.
- **1 outlook case**: the board looks ahead. Ten real cases claim the shelf — three hydraulic cases take every seal kit, two air cases draw filters the shelf covers, two wire-feed cases take the liner stock to exactly its shelf — and two obligations are earned the honest way, one retired before the projection. The outlook at a fixed moment must match the hand-computed book: the seal kit is short by 1, bitten by the standing obligation's cycle due inside the horizon (its bites date *is* the due date), the exactly-zero part is not a risk row, the retired obligation contributes nothing to a part whose shelf is empty, and the store's records stand byte-identical across the build.
- **1 gaps case**: what the plant doesn't know. Two feeder cases on a machine the plant model does not even register exhaust at `unknown_fault` — the first is then rejected at the gate (the row carries its history), the second still waits (the row is biting now). Between them run the two boundaries: a conveyor case that exhausts on an unseparated pair whose fault *has* an SOP, and a compressor case blocked on a part — neither is missing knowledge, so neither contributes a row. ### The reasoner regression gate: swapping models is a gated act

The loop's value lives in its reasoner, and providers change models constantly — a new Muse Spark point release, a cheaper fallback, a surface change. Swapping used to mean hoping; now it is a gate (`regression.py`, runner `evals/run_gate.py`):

- **Fixed suite, named configuration.** The gate drives the golden pack's 20 case entries — safety cases included — through one reasoner configuration (backend + model + surface, stamped on the record). Model calls are counted at the port; each case records its exit, rounds, top diagnosis, tokens and the two safety pins. The offline backend's record is the committed baseline (`evals/gate/baseline-offline.json`, served at `/evals/gate-baseline`).
- **A mechanical verdict.** `compare` diffs two records in code against criteria authored in one place, evaluated in order: the suite is whole → **safety pins** (a safety case that received any model call, or a converged plan missing a mandatory safety step, fails outright — safety is a criterion, not a metric) → **exit regressions** against a printed severity order (`converged > blocked_external > budget_exceeded > exhausted > safety_stop`) → **diagnosis agreement** ≥ 90%. Improvements and round/call deltas are reported, never gated.
- **The exercise partner.** A shipped stub candidate (`stubs.py`, labelled, and deliberately *not* selectable through `REASONING_BACKEND`) differs from the baseline by exactly one diagnosis (G14) and one extra round (G20): the gate PASSes it at 95% agreement, which is what a good swap looks like. Pin-breaking candidates are constructed in the tests only — a profile whose purpose is breaking safety is not shipped anywhere.

```bash
uv run python evals/run_gate.py run --backend stub --out evals/gate/candidate.json
uv run python evals/run_gate.py compare evals/gate/baseline-offline.json evals/gate/candidate.json
uv run python evals/run_gate.py check --backend muse   # a live swap, gated before it is trusted
```

## Closing the loop: outcomes

A gate decision says a draft may proceed. It does not say the draft was *right*. So the record stays open for what happened next, and the loop is measured against it:

- **Outcome capture** — `POST /api/cases/{id}/outcome` (and the form on the case detail in the console): the supervisor records the plan's disposition (`accepted` / `accepted_with_changes` / `rejected`), the **confirmed fault** from the same vocabulary the diagnoses speak, the work performed, the actual downtime, the parts used, and whether the case resolved. Validation is strict — an unknown fault class is a 422, because ground truth with a typo in it poisons every number downstream. Partial outcomes count for what they recorded.
- **The plant remembers** — a confirmed fault is written back to the machine's history, where the next diagnosis reads it. The write-back is a store record of its own (migration `0004`), never an edit to the packaged KB: the KB's seeded history stays immutable *recorded* history, and every written-back entry is marked `supervisor_confirmed` with the case that confirmed it — the two kinds are never confused. Only a confirmed fault writes (any disposition counts — the fault the floor found is ground truth even when the plan was refused; an outcome confirming nothing writes nothing), one entry per case, ever. A safety stop refuses a confirmed fault outright, before anything persists: a safety case has no diagnosis to confirm. The diagnose context carries the machine's merged history — confirmed entries first, sources marked — so the offline signals cite a confirmation as the floor's own finding, the model backends see it in their context marked the same way, and when the readings cannot separate two fault classes, a supervisor-confirmed precedent for the leader is the discriminating fact that separates them. Recorded history alone never separates anything; it is cited as evidence, nothing more.
- **Live diagnosis accuracy** — `GET /api/stats/diagnosis`: top-1/top-2 accuracy of the diagnosis against confirmed faults, per-fault-class precision/recall with their counts, mean rounds-to-converge for confirmed cases, plan-acceptance rates, estimated-vs-actual downtime error, and a downtime-economics section that prices the same comparison per line and plant-wide (see "The board in dollars" below). Pure aggregation over the records, identical over both stores; with no outcomes yet it says so instead of printing zeroes. A **learning-loop section** reports the write-backs (confirmed faults, by machine) and repeat-fault performance — the top-1 rate on cases whose machine + fault a supervisor had already confirmed, set beside the overall top-1 rate, both as plain counts; when there are no repeat cases yet it says so.
- **Shift handoff** — `GET /api/board/handoff` (add `?format=text` for the shift-log text): cases at the gate, escalations with their open gaps, blocked-external cases with the part they're waiting on (and, when the wait is the board's own allocation, the case holding the claim), safety stops, open reliability items, the faults supervisors have confirmed into the machines' history, the last board run — including what a budget cut left unworked — the carry-over manifest the next shift inherits (see "The next shift inherits the board" below), and the preventive-maintenance standing: obligations with their due points, proposals awaiting a decision, every deferral on record, and the retired obligations with the reasons they ended (see "From watch to work" below). Every fact is composed in code from the records; no model writes any of it.
- **Recurring-fault watch** — when a case reaches the gate, or an outcome confirms a fault, a code-side watch counts the same machine + fault class inside a rolling window (default: 3 in 14 days, `RELIABILITY_THRESHOLD` / `RELIABILITY_WINDOW_DAYS`). At the threshold it raises **one** `reliability_review` item on the board, carrying the contributing cases as evidence. Fixing the same bearing three times in a fortnight is a reliability problem, not three maintenance jobs — the item says so, and of itself does nothing else. What the pattern *earns* on top of the item is the preventive-maintenance layer — see "From watch to work" below.

## Parts reality: substitutions and the floor packet

A stocked-out part is where a demo ends and a plant tool begins. Two mechanisms handle it:

- **Substitute-part replanning** — substitution lives in the verify stage, not in any planner, so it runs for every backend and leaves paperwork. The KB carries an explicit **compatibility relation** per part slot (basis + spec deltas: rating, fit, grade), and SOPs carry **constraints** for a slot where the physics demands them. When the shelf cannot satisfy a requirement, the search walks the relation in order: not stocked or short → rejected; a spec that violates an SOP constraint — or can't be verified at all → rejected, reason named. The first candidate that clears both is applied: plan steps are revised onto it, the substitution is recorded as a plan element, and a converged plan that uses one is flagged **SUBSTITUTION** on the record and in the work-order draft — the supervisor approves it knowingly, or not at all. When nothing passes, the case still exits `blocked_external`, but the escalation documents the search: what was considered, and why each candidate failed.
- **Board-level allocation** — the board shares one shelf, and the loop plans like it. When a case converges, the parts its plan will draw are **claimed** for it in an allocation ledger (its own store table, migration `0005`), in board-run order — which is priority order by construction. Every later case measures the shelf *net of the claims standing*, in the parts pass and in the substitute search alike: a substitute claimed by an earlier case is exactly as unavailable as one the shelf never held. A case that loses a part to a claim takes the ordinary paths with the reason named precisely — its blocked gap reads "claimed by EXC-…, higher priority on this board", never a bare stockout that hides the board's own decision — and the shift handoff names the allocation and the claiming case. A gate **approval** leaves the claim standing (the work order will draw the part); a gate **rejection** releases it, stamped with the reason, the time and the supervisor, back into the pool for *future* runs. A release never rewrites the finished run it came from — runs are records; the case that blocked stays blocked on its record until a fresh run re-plans it. A claim is a planning reservation on the record, not a warehouse transaction: it draws no stock and marks no work performed, and safety cases never claim — they escalate at round 0, before any of this machinery exists. The ledger is on the board run record, at `GET /api/allocations`, and in the console's board view.
- **The work-order packet** — `GET /api/cases/{id}/packet` (JSON, or `?format=text`) renders a gated case for the technician who carries it to the machine: case summary, diagnosis with its evidence, the plan steps in order, the mandatory safety steps again as a **check-off list**, the parts list with substitutions flagged (basis and deltas included) and each part marked when it stands claimed for this case on its run, the estimated downtime, and blank sign-off lines — supervisor, technician, completion with actual downtime and parts used. Composed in code from the record only. Only a converged case packets: a non-converged exit produced an escalation draft instead, and a rejected draft must not reach the floor dressed as a work order — both are a 409. An awaiting case packets with its draft banner; an approved one carries the approval on its face.

## The board in dollars: downtime economics

The priority formula speaks in severity points. A plant runs on money per hour of downtime — and the supervisor, not the formula, is where a dollar judgement belongs. So every case is also priced, in code, from facts the loop already carries:

- **Rates are plant-model data** — each line in the bundled KB carries a `downtime_rate_usd_per_hour`, authored alongside its criticality like the SOPs and the shelf. Utilities (line-e) deliberately carries none: its downtime is not charged to a product line in this plant model, so its cases are **minutes only** — an absent rate is a fact, never a licence to invent one. Every dollar figure names the rate it used and where the rate lives.
- **Exposure** — a case's estimated exposure is its plan's own estimated downtime priced at its line's rate, stamped on the record when it reaches the gate, shown beside the case on the board and in the console, and totalled on the board run ("this board is carrying ~$19,053.33 of estimated downtime exposure" on the seeded board) with the largest single exposure named. The shift handoff carries the same section: open exposure, the largest open case, and the closed cases' recorded actuals.
- **Economics inform; they do not reorder** — exposure is printed beside the priority order, never fed into it. A $7,200 maintenance alert still works *after* a $633 line-down case, because the plant's triage doctrine is a safety-and-severity judgement, not a financial one. The supervisor sees both numbers and applies the overlay — that stays a human's job, and the golden pack pins the order to prove it.
- **Safety is never priced** — a safety stop carries no economics at all: not a zero, an absence. Its record, its board row and its handoff section stay exactly as bare of money as they were before this feature existed.
- **Cost accuracy** — when a supervisor records the outcome, the actual minutes are priced at the same rate the estimate used, and the stats report estimated-vs-actual minutes *and* dollars, plant-wide and per line, over the same population as the downtime error — counts beside every figure, and minutes-only cases counted in the minutes and never in the dollars.

## The next shift inherits the board: shift carry-over

A board run ends; the plant does not. Until this round, a run's unfinished business survived only as records plus handoff prose, and the next shift's board was assembled fresh, by hand, from the prose. Now the handover is a mechanic with the same standing as the loops:

- **The manifest** — when a board run ends, its unfinished business is computed in code and stored on the run record: cases the shift budget never reached (*not worked*), cases that exited `blocked_external` and still wait (*blocked*), and cases still awaiting the supervisor at the gate (*at gate*) — each with its state and what it is waiting on. The run record also carries every queued case's intake payload, so the offer is self-contained. The shift handoff gains the same manifest as a section: the contract the next shift is handed, not a summary of it.
- **Acceptance is explicit** — a new board run names its predecessor (`carry_over_from` on `POST /api/board/run`, `--carry-over-from` on the CLI) or it starts clean; there is no implicit inheritance. Acceptance settles the offer against the store *as it stands then* — decisions land between runs, and the settlement, not the manifest, is the truth. A case decided in the meantime is closed, not carried.
- **Re-work is a resume, not a re-intake** — a blocked case re-enters the loop at its loop-back point with its loop state intact: diagnosis, plan, open gaps, every round record, and its cumulative token spend. The next round is round N+1 against the same `max_rounds` bound — the budget governs the case's total work across shifts, not per shift — and the first resumed round re-diagnoses focused on the carried gaps, exactly as a loop-back round does, while the parts pass re-measures the shelf as it stands *now*. That re-measurement is the point: a stockout is a fact about a moment, and the moment has passed. Gate cases are inherited standing — a human is already their next step, so they consume no budget and are never re-worked — and unworked cases join as the fresh intakes they always were. Inheritance chains: a gate case one shift inherited and left standing is re-offered on that shift's own manifest, so an undecided case is never dropped from the chain by being inherited once.
- **Claims turn over with the board** — claims are run-scoped planning reservations, and the turnover adjudicates every standing claim in the ledger. An accepted case's claims are **renewed** into the accepting run, stamped `carried_from_run` with the hop's provenance, and stay releasable by a gate rejection exactly as before. A claim whose case is finished — decided and done, dropped, superseded — is **released** with the reason `released_run_ended`, and the settlement lands on the run record and in the handoff ("2 claim(s) renewed for carry-over, 1 claim(s) released — run ended"). One exemption, carried from the allocation round: a claim whose case is **approved and still awaiting its outcome** keeps standing — the approved work order will draw the part — and the first turnover after the outcome lands releases it. A part a finished board was holding is therefore provably free on the next board: the golden pack runs the contention board across two shifts and watches the blocked case take the freed belt.
- **Drops** — at acceptance the supervisor may drop a carried case (actor + reason, on the record): the case leaves the board with the drop stamped on it, and its claims release with the turnover. Dropping is the only way a case leaves the board without a gate decision, and it is never silent. A fresh submission of the same case at acceptance supersedes the carried entry instead — the new intake wins, the old claim falls to the sweep.
- **Safety carries as a record, never as work** — a safety stop that is still waiting carries as an *at gate* escalation for the human; it is never resumed into the diagnosis path, and the settlement refuses to build a resume seed for a safety case in code, not by convention. An unworked safety case carries as a fresh intake and stops at round 0 when the new board reaches it, exactly as it would have on the old one.
- **Records, not recounts** — a re-worked case's new record replaces its old one (one record per case, as always), so the stats and the economics read each case once, at its latest record: a case worked on two boards is one case in the plant's numbers, with its exposure recomputed from the same pricing functions — never summed across runs. No new storage was needed: run records, case records and claims already persist as payloads, and every field this round adds is additive with a default.

The manifest of any stored run is at `GET /api/board/runs/{run_id}/carry-over`, including how that run's own inheritance settled.

## From watch to work: preventive maintenance

The watch notices a machine faulting on a pattern and raises its item. An item changes nothing — the plant fixes the same bearing a fourth time. This layer is what the pattern earns:

- **Proposals, computed in code** — when the watch's recurrence rule fires for a machine + fault class (the same counting, read from the watch itself — there is no second recurrence definition), the system drafts a **preventive-maintenance proposal**: the machine, the fault class, the evidence *cited* — the contributing case ids with the moment each entered the record — and a proposed inspection interval derived from the evidence's spacing. The rule is authored plant-model data (`pm` in `kb.json`): **interval = 0.5 × the mean gap between consecutive cited faults, rounded to whole days and clamped to 3–30 days**. Every step of the arithmetic is printed on the proposal, so the supervisor decides on the numbers, not on a summary of them. Below the threshold, nothing is drafted — silence is the correct output. A proposal is a stored record (its own table, migration `0006`, on the board-items/part-claims precedent: a decision may land days after the draft, and a board run must find due obligations weeks after an approval).
- **The supervisor decides** — `POST /api/pm/proposals/{id}/decision` (console panel and CLI `pm-decide` too). **Approve** creates a standing **PM obligation** — at the interval the supervisor approves, which is editable at the gate; the approved interval is the one that stands, and both values stay on the proposal. The obligation's clock runs from the last performed inspection when the supervisor declares that date at approval (their fact, recorded as theirs), else from the approval itself. **Reject** requires a reason — and moves the **evidence watermark**: the cases the rejected proposal cited are spent, and a new proposal for the same machine + fault needs a fresh threshold of faults beyond them. A watch that re-nags the same evidence is a watch people mute. While a proposal waits undecided, or an obligation stands, no second proposal is drafted for that pair — the plant is already answering the pattern.
- **The board remembers the date** — when a board runs at or after an obligation's due point (last performed + interval), the obligation sends an ordinary `maintenance_alert` case onto the board: the existing loop works it, the existing priority formula ranks it (maintenance base — no parallel path, no special pleading), and it waits at the same gate. One open cycle per obligation; the case carries its provenance (obligation, proposal, interval, last performed, due date) on its face.
- **The outcome closes the cycle** — and only the outcome. An accepted outcome stamps the PM **performed** at the outcome's own recorded moment and sets the next due point a full approved interval later; the agent never marks work performed — approval alone leaves the performed stamp exactly where the supervisor's declaration put it. A rejected outcome is a **deferral**: the supervisor's reason rides in the work-performed note (the service refuses a reasonless one before anything saves), and the due point rolls forward **7 days** from the deferral — the authored deferral step, soon rather than a full interval, because the pattern that earned the obligation has not gone away. A cycle case dropped when the next shift accepts the board rolls the same way, on the drop's own by/reason. Deferrals land in the shift handoff, with their reasons, so an inspection that keeps being put off is visible in the log.
- **Evidence stays honest** — a PM cycle case is an inspection the system itself scheduled, so it never counts as a recurrence: not as evidence in a later proposal, not as a trigger. (The watch still counts case records exactly as it always has; the proposal layer cites faults, not inspections.) And the PM machinery never touches a safety case or its path — safety records carry no fault class to propose on, and the golden pack's safety entries are unchanged.

- **Retirement ends an obligation** — a standing duty is not immortal. A supervisor retires one (`POST /api/pm/obligations/{id}/retire`, CLI `pm-retire`, the console PM panel): actor and reason required, both on the record, and the retirement is **one-way** — there is no un-retire, the same no-un-ring discipline as the rest of the system. A retired obligation surfaces no further due cases, its cycles no longer close or roll, and its proposal's evidence joins the watermark: if the pattern genuinely returns, it earns a fresh proposal from fresh faults, and a fresh approval creates a *new* obligation. The retired record is never deleted — the handoff's PM section lists it with its reason, so a later shift can see what the plant stopped owing, and why.
- **Machines end too** — a supervisor decommissions a machine (`POST /api/machines/{id}/decommission`, CLI `machine-decommission`): actor and reason required, effective from a stated moment. The act is computed, not declarative. Its standing PM obligations retire automatically, each carrying the fixed reason **"machine decommissioned"** and the decommission record's id — an automatic ending, distinguishable from a supervisor's manual retirement forever. Its **open cases are listed on the record and nothing more**: the supervisor disposes each one (`POST /api/machines/{id}/dispositions`, CLI `machine-dispose`) — **keep** it (the loop keeps working it; a case about a scrapped machine can still carry a safety or quality lesson) or **close it as moot** (stamped on the case, its standing part claims released). No case is ever closed, dropped, or decided by the decommission itself — a safety case on the machine escalates exactly as before and can only be dispositioned by the explicit per-case choice. And intake closes: a new case naming the machine is refused where cases enter, with the state named — the board cannot gain work for a machine that no longer exists. Machine state is a stored record (migration `0007`), not plant-model data: `kb.json` stays authored and immutable, and the machine's safety records and history stay fully readable forever. Decommissioning removes a machine from the future; it rewrites nothing about its past.

Proposals and obligations are at `GET /api/pm/proposals` and `GET /api/pm/obligations`, retirements at `POST /api/pm/obligations/{id}/retire`, machines and their dispositions under `GET /api/machines` and `POST /api/machines/...`, all in the console's PM and machines panels under the board, in the handoff's PREVENTIVE MAINTENANCE section, and on the CLI (`pm-proposals`, `pm-obligations`, `pm-decide`, `pm-retire`, `machines`, `machine-decommission`, `machine-dispose`).

## The board looks ahead: the parts outlook

Every parts measurement so far was present-tense: a case blocks when its part is not there *now*, and the allocation ledger nets the claims standing *now*. But the record already knows a great deal about the near future — and a shortage discovered when a case blocks is discovered at the worst moment. The outlook (`outlook.py`) projects it, in code, over a stated horizon (14 days, authored, printed on every report; `?horizon_days=` widens or narrows it per call):

- **Three demand sources, every unit traced** — per part, the projected demand is the sum of (a) **standing claims**: parts the board has already committed to converged plans; (b) **open cases' unsatisfied plan requirements**: what cases still on the board will draw if they converge as planned — satisfied requirements a claim already covers are not counted twice, a satisfied-but-unclaimed plan draws on the part it names (the substitute, when it runs on one), and an obligation whose cycle case is already on a board counts through that case's plan, never twice; and (c) **PM cycles falling due inside the horizon**: each standing obligation's next due cycle, quantified by the parts its SOP names — the same SOP the cycle case itself will run. Later cycles are not projected: they stack speculation on an unperformed inspection.
- **Shortage rows, with the biting moment** — where projected demand passes the plant model's authored on-hand quantity, the part lands as a named shortage row with the shortfall and the earliest moment the shortfall **bites**, computed from the dated lines: demand already on the books (claims, open plans, overdue cycles) bites at the projection moment; otherwise the PM cycle whose due date tips the part over is named, with its date. A part at exactly zero shortfall is covered, not a risk — the boundary is pinned, not approximated.
- **Unquantified stays unquantified** — an obligation whose machine + fault class has **no SOP on record** cannot name its parts, and the outlook refuses to invent them: the cycle is listed as unquantified, with the reason. (An SOP that names *no* parts was consulted and names none — that contributes zero, silently.) Retired obligations contribute nothing at all: their due cycles are gone, and the projection believes the record.
- **A read model, nothing more** — the outlook creates no cases, places no claims and **orders nothing**: procurement is a human's job and stays out of scope here; the projection advises, the supervisor acts. The golden pack pins the store byte-identical across a build. Surfaces: `GET /api/parts/outlook`, the CLI `outlook` command, a console panel under the board, the demo's outlook section, and a **COMING PARTS SHORTAGES** section in the shift handoff — the next shift should see the shortage coming too, while it is still a date on a calendar rather than a blocked case at the workbench.

## What the plant doesn't know: the knowledge-gap report

Every block so far was handled honestly per case. What nobody could see was the pattern — the same missing knowledge blocking the third case this month. A case whose diagnosed fault has **no SOP on record** for its machine cannot be planned against the plant's own procedure, because there isn't one: the offline diagnosis derives its hypotheses from SOPs, so the record shows an `unknown_fault` with no evidence, a gap no round can close, and an exhausted case after every round is burned. The verify stage's safety check reads the SOP's mandatory steps — with no SOP there is nothing to check, and until now nothing *named* the absence. The knowledge-gap report (`gaps.py`) adds it up, in code, over the stored case records:

- **Grouped by the missing asset** — one row per (machine, fault) with no SOP, using the same `sop_for` test the loop and the parts outlook apply (referenced, not forked: the outlook's `unquantified_pm` is the same test over PM obligations). Each row carries the blocked-case count, the case ids in record order with the earliest and latest named, the **total rounds those cases burned** before blocking — the price of the hole, from the records — and whether a case is blocked on it *right now*. Rows rank open-now first, then by count. A row whose cases were all decided still lists: closed is history, not healed.
- **The advisory boundary** — the report advises the knowledge base's maintainer and generates **nothing adoptable**: no draft SOPs, no suggested safety steps, no proposed parts lists. Its schema carries identifiers, counts and timestamps only — there is no field that could hold SOP content, by construction, because a machine must never author the safety content a plant expert has not written. Authoring the SOP is a human's act, through the plant model's own workflow (an authored edit to `data/kb.json`, kept honest by the KB shape test). Standing PM obligations standing on the same hole are named on the row — the one authored SOP heals both.
- **Nothing unblocks itself** — a blocked case moves only through the existing flows (a supervisor's gate decision, or a fresh run that re-plans it; carry-over re-works the parts family, and an exhausted case carries as `at_gate`). What the report shows when an SOP lands is the future changing: new cases stop blocking, the row stops growing, and once every contributing record has been superseded by a re-run that converged, the row is gone — computed from the records, never by rewriting them.
- **The categories that are NOT here, on purpose** — an SOP that names no parts cannot block a case (and the outlook already ruled it consulted-and-none, not a hole); machines carry no criticality to miss (criticality is a line attribute, and every line has one); a part absent from the inventory register cannot be told apart from a planner inventing one (the golden pack's defective-planner case does exactly that), so parts blocks stay in the outside-world family where the handoff names them.
- **A read model, purely** — building the report writes nothing and calls no reasoner; the tests pin the store byte-identical across a build and the reasoner count unmoved. Surfaces: `GET /api/knowledge/gaps`, the CLI `gaps` command, a console panel under the board, the demo's gaps section, and a **KNOWLEDGE GAPS** section in the shift handoff — the incoming shift should inherit the pattern, not just the latest escalation.

## The supervisor edits, the machine re-checks: gate amendments

Until now the gate offered a supervisor two moves: approve the plan as proposed, or reject it and send the case back around the loop. The common case on a real floor is smaller than either — *swap this part for the one on the shelf, drop the step that doesn't apply here*. Amendments (`amendments.py`) are that third path, built so the small fix cannot quietly weaken the whole discipline:

- **An amendment is a record, not an edit** — it names its kind (`part_swap` or `step_strike`), its supervisor and its reason, and appends to the case's record. The loop's original plan is never modified; every surface that shows the plan — the packet, the console, the API's `effective_plan`, the parts outlook — shows the amended plan *derived* from the original by replaying the passing amendments, with each change marked (what changed, by whom, why). A failed amendment is on the record too: the attempt and the verdict are both kept.
- **Re-verification is code, run at recording, before any approval** — the amended plan goes back through the verify stage's own checks (`guardrails.verify_plan`: mandatory safety steps complete, parts real, no banned actions, no SOP contradictions) with every requirement re-measured against the shelf net of *other* cases' claims, plus the substitute search's SOP-constraint test for a swapped part. No model is consulted — a counting-reasoner test pins zero reasoning calls across the amendment path. A failure sits on the case's face as **AMENDMENT_FAILED**, and the approve path refuses it: the supervisor amends again, or rejects.
- **The vocabulary is deliberately small, and each limit is a refusal with a name** — a swap names a part from the plant register *by id* (a free-text part is refused: it cannot be checked against a shelf, a spec sheet or an SOP); a strike names a non-mandatory step (striking a mandatory safety step is refused, naming the step and its SOP — an amendment may redirect a plan, never thin its safety steps); and there is **no way to add a step**, because an added step has no diagnosis behind it: the supervisor directs the work, the planner proposes it, and new steps come from the loop on a fresh run, not from the gate. Anonymous and reasonless amendments are refused the same way.
- **Compatibility paperwork, honestly sourced** — a swap carries its basis and spec deltas the way a verify-stage substitution does: the KB's authored basis and deltas when the pairing is listed for the slot, the plain statement that the pairing is supervisor-specified and unlisted (with deltas computed from the two spec sheets) when it is not, and "the slot's own part" when the supervisor swaps back. A candidate that fails the SOP's constraints for its slot fails verification with the deltas named — the seeded fan pairing (380 m³/h against the 420 floor) fails exactly this way.
- **Claims follow the verified plan** — a passing swap moves the case's allocation in the same act: the old part's claim is released stamped `released_by_amendment`, the new part claimed under the case's run; a swap onto a part another case holds fails naming the holder, and passes once that claim is released. A failed amendment moves nothing. The diagnosis stats count the gate's work as its own facts (amendments recorded, passed, failed, approvals of amended plans) — never folded silently into the loop's numbers. Surfaces: `POST /api/cases/{id}/amendment`, the CLI `amend` command, the console's amendments section, the demo's `[AMENDMENT]` beat (a strike that lands, and the lockout strike the gate refuses), the packet's marked parts and amendments section, and an **AMENDED AT THE GATE** section in the shift handoff.

## The fault that came back: recurrence links

A machine fault the plant solved last week can come back this week — and until now the new case started cold: the confirmed fault sat in the machine's history as one marked entry among its notes, the watch counted patterns at the gate, and the stats scored repeats after outcomes landed, but nothing tied the new case to the specific closed case it repeats. Recurrence links (`recurrence.py`) make that tie, in code, at diagnosis time:

- **Detection is a rule, stated exactly** — the moment a case's first diagnosis lands, its top fault is the join key: code looks for an earlier case on the same machine whose recorded outcome *confirmed that same fault* — the write-back's own line, so an accepted case and a rejected-but-confirmed case both qualify, because the floor's finding is ground truth either way — inside a fourteen-day window, the fortnight the recurring-fault watch already counts in, so the plant keeps one calendar for "again, soon". What never seeds a link: an outcome that confirms nothing (the misdiagnosis close — nothing was proven, so nothing can recur), a case with no outcome yet, a dropped or moot-closed case, a safety stop, an undatable episode, and the case itself. The most recent qualifying prior wins.
- **The head start is an episode, not a nudge** — the link rides the new case's record (prior case, its diagnosis, its outcome and resolution, the work note, the spacing in days) and enters the diagnosis context as one labelled chunk, framed as history rather than instruction, so every later round — and the plan drafting — meets the prior episode whole. The reasoner may agree or depart; nothing anywhere steers its diagnosis toward the prior, and when the loop converges in one round the link still forms and informs the plan and the gate. The link is sought once, against the first diagnosis: a diagnosis that arrives at the fault only in later rounds gets the merged-history context it always had, but no link — and that miss is final for the run.
- **Departure is marked, never blocked** — the verify stage is untouched (no new check, no new gap kind): a settled diagnosis that differs from the prior's confirmed fault stamps the record **DIAGNOSIS_DEPARTED_FROM_PRIOR**, printed on the console, the packet and the handoff, and the case approves or not on exactly the merits any case has — the prior confirmation could itself have been the wrong call, and the outcome loop is where that gets judged.
- **Counted at the gate, from the records** — the diagnosis stats gain a recurrence section (links made, by machine, and the agreement rate over settled links) that reads the link overlays and nothing else: measured when the case reaches the gate, where the learning-loop section measures the same habit after outcomes. The handoff names the waiting recurrence cases with their priors. And the bookkeeping stays single: a linked case that blocks on a missing SOP is one knowledge gap in the gap report, counted once, as itself. The prior record is never modified by being linked from — the tests pin it byte-identical.

## Saturday's four hours: downtime windows

The board ranks the work, and the shift budget rations the *agent's* work — cases and tokens. Neither answers the floor's standing question: the line stops Saturday 08:00 for four hours; which work goes into those hours, in what order, and what is honestly left out? Downtime windows (`windows.py`) answer it the way everything else on the board is answered — in code, from the records:

- **Declared by a supervisor, planned in code** — a window is a start, a length in minutes, and a scope in the plant model's own ids (named lines and/or named machines; an unknown id is refused by name, not silently dropped). Declaring is an act with a named actor, and the plan is computed in the same act. Windows are records in their own table (migration `0008`): a window declared Tuesday is confirmed Thursday, and a later window's planning must find the earlier one's bookings where they live.
- **Work-ready means work-ready** — a case enters the packing only when its plan converged, a supervisor has *approved* it at the gate (a case still awaiting its decision is not ready — the window never pre-empts the gate), no outcome is recorded yet, and the allocation ledger's standing claims cover the plan as it stands at the gate — read from the ledger at planning time, never assumed from the approval. A safety stop is never work-ready: it was escalated at round 0 precisely because it is not work to schedule.
- **One ranking, honest arithmetic** — cases pack in the board's own priority order (the score stamped on the record); PM obligations due within the window's span compete for the same minutes on the same footing, scored by the same formula read as the maintenance alert their cycle case would be. Estimates are the plans' and SOPs' own stated downtime — authored planning figures, labelled as such, never presented as measurements. Packing is greedy in priority order and never reorders to fill a gap: an item that doesn't fit the minutes left is **deferred** with its shortfall printed, an item longer than the window itself is **oversized**, and an item with no estimate on record is **unestimated** — listed by name, never silently given a number. The plan shows its own arithmetic: minutes used, minutes left.
- **A proposal until a supervisor confirms it** — confirmation re-reads the state the plan was computed over (a fingerprint over every candidate, taken at computation). If the board has drifted — a packed member decided, outcomed, dropped, or stripped of its claims since — confirmation refuses, naming the drift, and re-planning is the remedy. A confirmed window books its packed items: an overlapping window planned later lists them as booked elsewhere rather than double-booking the same work. And the window is an overlay, not a second decision: planning and confirming change no case record (the tests pin them byte-identical), open no PM cycle, and move no claim — the cases in a confirmed window still end at their own gates. The shift handoff names the confirmed windows still ahead, read-only, and the window statistics are counts — planned, proposed, confirmed — with no utilisation KPI invented from the arithmetic that already sits on each plan.

## Honest status

- **Muse Spark adapters are built to Meta's documented API and unit-tested against stubbed transports** (Chat Completions request shape; Responses shape; the round-1 encrypted reasoning item verifiably rides along on round 2). **Live verification is pending a Model API key** — no live call to `api.meta.ai` has been made from this repo yet, and nothing here claims otherwise. The offline backend runs the identical loops today. When a key lands, the first live run does not go straight to the board: it goes through the reasoner regression gate (`evals/run_gate.py check --backend muse`, on each surface) against the committed offline baseline, and the profile is trusted only on a PASS — that gate is the promotion path, not a formality after it.
- **Docker/compose not run in the build sandbox** (no daemon); the topology mirrors the sibling blueprints' verified compose stacks, and the Dockerfile builds from the same frozen constraints. First `docker compose up --build` on a real machine is the check.
- **PostgreSQL paths are covered by gated tests** that skip without `TEST_DATABASE_URL`; they ran against the doubles everywhere else.
- The offline backend is a rules engine, not a model: its diagnoses are only as good as the SOP thresholds in the synthetic KB. It exists so the loops can be evaluated deterministically — swap in `muse` or `llm` for real reasoning.
- The KB, histories, inventory and board are synthetic. A real deployment points the ports at the plant's CMMS/EAM, document store and historian; the loop code does not change.

## Extension seams

- **New reasoning backend**: implement the three-method `Reasoner` protocol and register it in `backends.get_reasoner` — the loops never see the difference. Then gate it: `evals/run_gate.py check` against the committed baseline before the profile is trusted with a board.
- **Real plant systems**: replace `KBRetriever` (SOPs/history/inventory reads) and the `Store`/`ObjectStore` implementations behind their ports; keep the controllers.
- **Loop policy**: rounds, budgets and the priority weights live in `loops.py`/`priority.py` config, not scattered through the graph.
- **Actuation**: deliberately absent. If a deployment ever connects the gate's approval to a CMMS work-order API, that integration belongs behind the supervisor's decision — the agent's boundary does not move.
