# Architecture — Plant Operations Loop Agent

## The design in one paragraph

A shift's exceptions live on a board. Two nested loops work that board, and both loops are **controlled by code, not by the model**: the model is called for three bounded judgements per pass (diagnose, plan, critique) and everything else — which case is next, whether a plan is acceptable, when to stop, what happens to the record — is deterministic code with tests. The outer loop decides *what to work on*; the inner loop decides *when a case is done being thought about*; a human decides *what actually happens*.

## The board loop (outer)

```
        ┌──────────────────────────────────────────────────┐
        │                                                  │
        ▼                                                  │
  order (priority, code) ──► select next ──► run case loop ──► record at gate
                                │
                                ├─ queue empty ────────────► BOARD_CLEAR
                                └─ budget spent ───────────► SHIFT_BUDGET_EXCEEDED
                                                             + written handoff
```

- **Ordering** (`priority.py`): base weight by exception type — `safety_observation` 1000, `machine_down` 600, `quality_nonconformance` 400, `material_shortage` 250, `maintenance_alert` 150 — scaled by `1 + 0.25 × (line_criticality − 1)`, plus for `machine_down` half the minutes already down (capped). Ties break by `reported_at`, then case id. The formula and its reason string are stored on every record: anyone can recompute why a case went first.
- **Budget** (`BoardPolicy`): max cases and a token budget for the run, checked in code before each case. A case mid-loop is never cut off; the budget binds *between* cases.
- **Handoff**: on a budget exit, the unworked remainder is listed with each case's own reason ("shift case budget reached (3 cases)"), the worked cases are grouped by exit, and the summary states plainly that everything worked waits at the gate and nothing was actioned. The handoff is data on the run record, not a log line.
- Implementation: a LangGraph graph (`order → select → process → select … → handoff`) whose `process` node invokes the case graph per case with gate mode *record* (see below), persisting each record via callback as it completes.

## The case loop (inner)

```
 intake ─► screen ─► prepare ─┬─ safety_observation ──────────────► draft (escalation)
                              │
                              ▼
              ┌──► diagnose ─► plan ─► verify ──┐
              │                                 │ gaps, rounds left,
              │        focus = open gaps only   │ budget left
              └─────────────────────────────────┘
                    verify's parts pass runs in code inside the
                    verify stage: shelf truth → KB substitute search
                    → replan around a passing substitute, or the
                    search is documented and the case blocks
                                                │ exit decided in code
                                                ▼
                              draft (work order | escalation) ─► SUPERVISOR GATE ─► record
```

### Rounds

Each pass is three calls behind the `Reasoner` port (`ports.py`), each returning a strict schema (`schemas.py`), each validated in code with one bounded retry:

1. **Diagnose** → `Diagnosis`: ranked `Hypothesis` list. Contract: every hypothesis carries `evidence` (SOP clause, history match, or reading) and a `confidence`. Retrieval over the KB (SOPs + history, behind the `Retriever` port) is scoped by machine before the call. The context also carries the machine's **merged history** (`CaseContext.history`, assembled by `history.py`): the KB's recorded entries plus the supervisor-confirmed write-backs for that machine, confirmed first, every entry marked with its `source` — and the same entries ride the prompt context as chunks, marked in text, for the model backends. The machine's own history is context by right, not by retrieval luck.
2. **Plan** → `ActionPlan`: ordered `PlanStep`s built on the leading hypothesis's SOP, `required_parts` named from the SOP, estimated downtime. The SOP's mandatory safety steps are inserted by the planner as steps with `kind="safety"`, `mandatory=True` — and the verify round treats their absence as a blocking safety gap, so "the model forgot the lockout" cannot converge. Parts are deliberately *not* resolved here: a planner's stock claims (including any substitute it names) are treated as unverified claims, and the verify stage re-measures them.
3. **Verify** → `Critique` (the model's own second look) **merged with code checks** (`guardrails.verify_plan`): `missing_safety_step`, `part_unavailable`, `unevidenced_hypothesis`, `sop_contradiction`, `banned_action`. Merge rule: code gaps win — where both flag the same `(kind, ref)`, the code version is kept; the model's critique can add gaps, never remove a code gap. First, though, the verify stage runs its **parts pass in code** (`substitution.py`):

   - **Shelf truth.** Every requirement is re-measured against inventory — `available_qty` and `satisfied` come from the shelf, never from the planner.
   - **The search.** For a requirement the shelf cannot satisfy, the KB's compatibility relation for that slot is walked in order. Each entry carries the pairing's basis and its spec deltas; SOPs carry `part_constraints` for slots where physics demands them (the COMP-7 fan slot requires airflow ≥ 420 m³/h). A candidate that is not stocked, is short of the required quantity, violates a constraint, or lacks the spec to even be checked is **rejected**, with the reason named.
   - **Replanning.** The first candidate that clears shelf and constraints is applied: plan steps are revised onto it, the requirement is satisfied *by substitute*, and a `Substitution` record (original, substitute, basis, spec deltas, outcome) rides on the plan. The code checks then measure the *revised* plan, and a critic's part gap for a part the pass resolved is retired as stale. When nothing passes, the surviving `part_unavailable` gap's detail is rewritten to document the search.

### Loop control (`loops.CaseLoopController`)

- After each verify, the controller computes the round's **gap delta** (opened/closed vs the previous round, keyed `kind:ref`) and records a `RoundRecord` — the loop timeline the console renders.
- On a loop-back, the next diagnose/plan receive **only the open gaps as focus**. Reasoners are expected to work the gaps (the offline rules engine applies discriminating checks for focused rival hypotheses — readings first, then the plant's confirmed memory: a supervisor-confirmed precedent for the leading fault separates a rival the readings could not, re-scored to the ruled-out level with the precedent named in its evidence; the model prompts carry the gap list verbatim). Focus is also where the Responses adapter's reasoning continuity pays off: round N+1 resumes round N's thread.
- Per-round token use is sliced from cumulative usage, so telemetry per round is exact, and the case budget is enforced on real numbers.

### Exit conditions (all in code, `decide_exit`)

Evaluated in this order after every verify round (and at prepare for the first):

| Exit | Condition | Draft |
|---|---|---|
| `safety_stop` | Case type is `safety_observation` (at prepare, round 0 — the case is never diagnosed), **or** any open gap is a safety-flagged `banned_action` | escalation |
| `blocked_external` | A `part_unavailable` gap survives whose part the verify stage's own search could not cover — no substitute listed, none in stock, or every candidate rejected by the SOP's constraints — more rounds cannot fix a shelf; the escalation documents the search | escalation |
| `converged` | No open gaps after verify | work order |
| `budget_exceeded` | Cumulative case tokens exceed `LOOP_CASE_TOKEN_BUDGET` with gaps still open | escalation |
| `exhausted` | Round count reaches `LOOP_MAX_ROUNDS` (default 3) with gaps still open | escalation, gaps named |

The ordering matters: a safety stop outranks a blocked shelf; a clean verify converges even if the budget is nearly spent; a hopeless part exits in round 1 instead of burning three rounds to reach the same escalation.

### The supervisor gate

Every case — converged or escalated, including safety stops — ends `awaiting_supervisor` with its draft. In the case graph this is a LangGraph **interrupt** before the decision node: the run pauses, the record persists, and `record_decision` either **resumes** the graph (checkpoint live) or **applies the decision directly** to the stored record (checkpoint gone — API restart, checkpoints off). Both paths produce the same record; the record is the source of truth. Board runs use *record* mode (no pause) because a board run must finish; the gate state is identical, only the pause differs.

The gate is a hard boundary, stated on every record (`GATE_NOTICE`): the agent never issues commands to machines, never marks work performed, never closes a case. A guardrail also screens the draft text itself for performed-work phrasing ("we replaced…", "back in production") — a draft that claims the work happened fails its own record's checks.

**The work-order packet** (`packet.py`, `GET /api/cases/{id}/packet`, JSON or `?format=text`): the floor copy of a gated case, composed in code from the record only — case summary, diagnosis with evidence, plan steps in order, the mandatory safety steps again as a check-off list, the parts with any substitution flagged (basis and spec deltas) and each part marked when it stands claimed for this case on its run, estimated downtime, and blank sign-off lines (supervisor / technician / completion with actual downtime and parts used). Only a converged case packets — a non-converged exit or a rejected draft raises a 409, because an unverified plan must not reach the floor dressed as a work order. An awaiting case packets under its draft banner; an approved one carries the approval on its face.

## The shared shelf: allocation (`allocation.py`)

Until round 5, the verify stage's parts pass measured the shelf per case, independently — correct for a lone case, wrong for a board. Two cases could both plan around the same last unit of a part, both converge, and the conflict surfaced at the workbench. Round 5 makes the board plan against one shelf:

- **Claims.** When a record is persisted at the gate (`service._persist_case` — the one funnel every gated record passes through, board graph and single runs alike), a converged record claims one entry per satisfied requirement, on the part actually drawn (the substitute, when the plan runs on one; the requirement it satisfies is kept on the claim). Cases reach the gate in board order, so claims follow the board's priority by construction — a case can only ever lose a part to an earlier, higher-priority case. The claim id derives from case + drawn part, so re-persisting a record claims once. Only converged records claim: `safety_stop` records in particular never hold a part, and the claim machinery sits entirely downstream of the loops, so it cannot delay or alter a safety path.
- **Effective stock.** The case controller reads shelf truth through two providers the service binds to the ledger (the same binding idiom as the merged-history provider): a stock provider (`effective_qty` = shelf − outstanding claims) and a claim-note provider. Both the parts pass and the substitute search — and the blocked-exit recheck, so the exit decision can never disagree with the pass — measure through them. Unbound (plain-code controller use, unit tests), the providers default to the bare shelf and behaviour is exactly the pre-round-5 behaviour.
- **Naming the claim.** When a shortfall is a claim's doing — the bare shelf could satisfy the requirement, the effective shelf cannot — the blocked gap and any substitute rejection carry the note `claimed by <case>, higher priority on this board` (for a claim left standing by an earlier run, the note names that run instead). The claimer is computed by walking the part's claims in recording order to the one whose quantity first makes the remainder insufficient. A shortfall the bare shelf also cannot satisfy keeps the plain stockout wording: the ledger never blames a claim for a shortage it did not cause. The shift handoff reads the claimer back out of the blocked record's gap text, so it reports the truth of the run that blocked even after the claim has been released.
- **Release.** Gate decisions land in `service.record_decision`, on both the resume and direct-apply paths: a rejection releases the case's standing claims, each stamped `released_by_gate_rejection` with the time and the deciding supervisor; an approval leaves them standing, because the approved work order will draw the parts. Released quantities return to the effective pool for *future* runs and re-plans only — a finished board run is a record and is never recomputed, so the neighbour that blocked on the claim keeps its blocked record until a fresh run re-plans it. That asymmetry is deliberate: the alternative (silently unblocking a case nobody re-verified) would put an unverified plan back in play. Since round 7 there is a second release path — the board turnover (`released_run_ended`, see the carry-over section) — and one revival rule that keeps the ledger honest across both: a released claim row never blocks a legitimate re-claim. If the same case later converges on the same part again (re-planned after a rejection, or freshly submitted after a turnover), `claim_from_record` revives the row as a fresh claim of the new run rather than leaving the case silently claimless; while a claim stands, re-persisting still claims exactly once.
- **Storage.** Claims are their own store collection (migration `0005_part_claims.sql`), following the board-items/history-entries precedent: the ledger is plant-wide runtime state that later runs must read and a later gate request must mutate, so scattering it across case payloads would make "what is outstanding?" a scan of other records' contents. The full claim rides as a JSONB payload with promoted `case_id` / `part_id` / `status` columns; the in-memory double keeps the same shape.
- **Boundary.** A claim is a planning reservation on the record. It is not a warehouse transaction, it draws no stock, and it changes nothing about the gate: the agent still never marks work performed, and the packet's claim marking exists so the technician sees the unit is spoken for — by this work order, against the rest of the board.

Surfaces: the board run record and its API response carry the run's claims; `GET /api/allocations` returns the whole ledger; the console's board view renders both; the packet marks claimed parts; the handoff names allocation-blocked cases. Diagnosis stats do not read claims — allocation is a planning fact, not an accuracy fact.

## The board in dollars: economics (`economics.py`)

Round 6 prices the board. The severity formula's points tell a supervisor what the plant's doctrine says to work first; they say nothing about what the board is costing, and on a real plant that number — money per hour of downtime — is the one the shift is managed against. The pricing is deliberately kept *beside* the order, never inside it:

- **Rates as data.** Each line in the plant model (`data/kb.json`, read via `kb.line_downtime_rate`) carries a `downtime_rate_usd_per_hour`, authored with the rest of the plant model — the same status as the SOPs and the shelf, editable in exactly the same way. Utilities (line-e) carries none, a modelling choice stated where the data lives: its downtime is not charged to a product line. A line with no rate yields minutes and no dollars, at every surface, forever — the code has no path that invents a rate, and every dollar figure carries its `rate_basis` (the line and the file the rate lives in) so a number can be traced to its source.
- **Per-case exposure.** `for_record` prices a case from facts the record already carries: the plan's `estimated_downtime_min` × the line's rate. A record with no plan has no estimate (0 minutes; the stats population, like the downtime block's, only ever averages records that carry a plan). The snapshot is stamped on the record at the one persistence funnel (`service._persist_case`) and refreshed in `record_outcome`, where the actual minutes are priced at the *same* rate — estimate and actual dollars on one record are always the same arithmetic, so their difference is an accuracy fact, not a currency artefact.
- **Board totals.** `board_summary` sums a record set the way the handoff and the run record need it: rated dollars and unrated minutes in separate piles that never merge, the count of cases in each, and the largest single exposure (earliest in the caller's order wins ties — callers pass board/gate order, so the named case is the first one the supervisor meets). On the seeded board the run carries ~$19,053.33 over 775 estimated minutes, 90 of them unrated.
- **No reordering.** `priority.py` does not import this module and no economics figure is an input to any ordering, exit, or gate decision — pinned by a golden entry in which a $7,200 maintenance alert is entered ahead of a $633 line-down case and is still worked second. The reasoning is doctrinal, and stated in the module: triage order encodes safety and severity judgements that money must not silently override; the dollar overlay belongs to the supervisor, who sees both numbers.
- **Safety is never priced.** `for_record` returns `None` for a `safety_stop` record — not a zero figure, an absence — and totals skip such records before counting anything, so a safety case contributes neither dollars nor minutes to any economics surface. The claim machinery precedent (round 5) is the same shape: safety paths stay untouched by later machinery, by construction rather than by care.
- **Cost accuracy.** `stats.py` gains an `economics` section over exactly the downtime block's population (outcomes with a recorded actual on a case that carried a plan): per-line rows (rate, counts, estimated/actual minutes and dollars, signed and absolute mean errors) and a plant block in the same shape, with the module's standing honesty — counts beside every figure, and an explicit note naming how many cases are minutes-only when any are. The handoff's section is the operational mirror: open exposure over the awaiting records, the largest open case, and the closed cases' actuals (rated dollars, unrated minutes, counts), rendered from the same dict into JSON and text so the shift-log paste cannot drift.

Surfaces: the record (and with it the API, the packet-adjacent reads and the console's case detail), the board read model (`store.board()` rows carry the case's minutes, rate and exposure, computed from the record at read time), the board run record, the stats payload, the handoff, the console's board table / run block / stats panel, and the demo's board narration. No migration: the snapshot rides the record's JSONB payload like the outcome does.

## The next shift inherits the board: carry-over (`carryover.py`)

Rounds 1–6 all end at the same place: a board run finishes, and its unfinished business survives only as records plus handoff prose — the next board is assembled fresh, by hand. Round 7 makes the handover a mechanic. The design turns on one distinction: the **manifest** is an offer, the **settlement** is the truth.

- **The manifest, computed in code.** When a board run ends, `compute_manifest` reads the run payload against the store's current records and classifies what is unfinished: `not_worked` (the shift budget cut the case before the loop reached it — no record exists), `blocked` (exit `blocked_external`, still at the gate), `at_gate` (any other exit, still at the gate — converged plans, escalations, safety stops). Each entry carries the case's rounds used, its standing claim ids, and a `waiting_on` sentence composed from the record (the budget reason; the unsourced parts; the escalation's open gap kinds; for a safety stop, explicitly *a record for the human, never re-worked*). The manifest is stored on the run record, which also gains `case_payloads` — every queued case's intake payload, worked or not — so the offer is self-contained and settlement never depends on re-deriving an intake. Recomputing the manifest later agrees with the stored one on the cases that are still unfinished, because both read the store as it stands.
- **Acceptance is explicit, and settles against the present.** `run_board(..., carry_over_from=<run id>)` is the only inheritance path; a run that names no predecessor starts clean, byte-identically to before this round. Settlement revalidates every manifest entry against the store *at acceptance*: a case decided since its board ended (approved, rejected, dropped) is `closed` and does not carry. What carries is dispatched by kind — below. A drop naming a case outside the manifest is a `ValueError` (409 over HTTP); an unknown predecessor is a `KeyError` (404).
- **Blocked cases resume; they are not re-intaked.** The settlement builds a resume seed from the stored record — diagnosis, plan, open gaps, all round records, cumulative token spend — and the board graph's queue carries it beside the case payload (`{"case": ..., "resume": ...}` wrappers; the case graph's `prepare` node overlays the seed onto the fresh run state). The loop therefore re-enters at its loop-back point: the next round is round N+1, `max_rounds` and the case token budget bound the case's *total* work across shifts, and the first resumed round re-diagnoses focused on the carried gaps — exactly what a loop-back round does — while the verify stage's parts pass re-measures the shelf as it stands now. Nothing is re-derived cold, and nothing is waved through: if the part is still unavailable, the case blocks again, with its round count grown. The context (KB retrieval, merged machine history) is prepared fresh — the plant may have learned something since the case last ran.
- **Gate cases are inherited standing.** An `at_gate` case consumes no budget in the accepting run, is not queued, and its record is untouched; it appears in the run's settlement so the accepting shift's record shows what it took on. Inheritance chains: a run's manifest re-offers the gate cases it itself inherited and left standing (read from its own `carry_over_settled`), so an undecided case survives any number of quiet shifts.
- **Claims turn over.** Renewal re-homes an accepted case's standing claims to the accepting run (`allocation.renew_for_case`), stamping `carried_from_run` with the run they came from — one hop of provenance per renewal — so `claims_for_run` stays truthful and the claim-note provider can name a carried claim as carried ("claimed by X (carried over from board run Y)"). The sweep then adjudicates *every* standing claim in the ledger, because a claim is a shelf fact, not a board fact: it survives only if renewed at this turnover, or its case is approved with the outcome still outstanding (round 5's rule — the work order will draw the part — now enforced at turnovers as well as respected by them), or its case still waits at a gate outside this board's scope (a single run's case; its own turnover or gate decision will adjudicate it). Everything else — decided and done, rejected, dropped, superseded by a fresh submission at acceptance, orphaned — is released with the new reason `released_run_ended`, stamped with the accepting run as the actor. The settlement (renewed and released claim ids, per-case dispositions) is stored on the accepting run's record and summarised in its handoff summary and in the handoff report's carry-over section.
- **Drops.** A drop at acceptance (`{case_id, by, reason}`) stamps the record — status `dropped`, a `dropped_from_board` block with both run ids, the actor, the reason, the time — and releases its claims under the turnover reason with the dropping supervisor as the releaser. The case leaves every gate surface at once, because they all filter on `awaiting_supervisor`. A dropped `not_worked` case has no record to stamp; the settlement entry is its audit trail.
- **Safety.** The re-work subset is `blocked_external` only, and settlement refuses — in code — to build a resume seed for a `safety_observation` or a `safety_stop` record: such an entry is inherited at gate instead. A safety stop therefore carries as an escalation record for the human across any number of shifts and never re-enters the diagnosis path through carry-over; an unworked safety case carries as a fresh intake and stops at round 0 on the new board, with zero model calls, exactly as it would have on the old one.
- **No double counting, by construction.** Case records are one per case id (store upsert): a re-worked case's new record *replaces* the old, so the stats and economics populations — always computed over `store.all_cases()` — read each case once, at its latest record and latest economics snapshot. A case worked on two boards contributes its final exposure once; the golden pack pins the population (`cases_total` stays 4 across the two-run contention scenario).
- **Storage: no migration.** Board runs, case records and claims already persist as JSONB payloads; everything this round adds — `carry_over`, `carried_from`, `carry_over_settled`, `case_payloads` on the run payload; `dropped_from_board` on the record; `carried_from_run` on the claim — is an additive field with a default, so payloads written before this round validate unchanged, and the endpoints answer for them with empty sections.

Surfaces: `POST /api/board/run` (`carry_over_from`, `drop`), `GET /api/board/runs/{run_id}/carry-over` (a run's outgoing manifest + its own settlement), the handoff's carry-over section (JSON + text), the run record's `handoff_summary` turnover lines, and the CLI (`board --carry-over-from`, `--drop`, `--by`, `--reason`). The console is unchanged — the board it renders already shows the inherited cases at the gate, because they never left it.

## From watch to work: preventive maintenance (`pm.py`)

The watch's item is a notice. Round 8 builds the follow-through the notice earns, and its design turns on keeping every judgement where it already lives: recurrence stays the watch's, priority stays the formula's, performance stays the supervisor's.

- **One recurrence definition.** `ReliabilityWatch.contributing_cases(machine, fault, now)` is the watch's counting, extracted as a named method its own threshold check reads. The PM layer cites that set; it never recounts. Evaluation runs wherever the watch is checked — `_persist_case` and the end of `record_outcome` — so a pattern completed by a supervisor's confirmation drafts its proposal at the same moment the item would raise.
- **Eligibility is subtraction, not a new rule.** From the contributing set, the proposal layer removes (a) cases a *rejected* proposal for the pair already cited — or the cited cases of the proposal whose obligation a supervisor has since *retired* — the **evidence watermark**, the union over those proposals, so re-proposal needs a fresh threshold of faults beyond everything already decided or ended — and (b) PM cycle case ids, because an inspection the system scheduled is not a fault recurrence. What remains must still meet the watch's threshold on its own. A pair with an undecided proposal or a standing obligation drafts nothing further: the plant is already answering the pattern. (Retirement itself is the lifecycle layer — next section.)
- **The interval rule is plant-model data.** `kb.pm_policy()` reads the authored `pm` section of the plant model — fraction 0.5, bounds 3–30 days, deferral roll 7 days — the way line rates are read: no env override, a deployment carries them in its own plant model. `interval_arithmetic` returns every intermediate (gaps, mean, raw product, rounding, clamp flag) and the proposal stores and prints them all; a supervisor can re-derive the number from the record alone.
- **Decisions and clocks.** Approval records both intervals (proposed on the proposal, approved as the standing one) and creates the obligation. Its clock basis is explicit on the record: `last_performed` when the supervisor declares that date at approval — a human-supplied plant fact taken at a human gate — else `approval`. Due = basis + approved interval. Rejection requires a non-empty reason (the API returns 409 without one) precisely because it spends evidence: the record must say why.
- **Surfacing is ordinary board work.** `run_board` settles carry-over first (a dropped cycle case rolls its obligation there, on the drop's by/reason — see below), then asks `PmManager.due_cases()` for obligations at/past due with no open cycle. Each sends an `ExceptionCase` of type `maintenance_alert` — priority from the existing formula's maintenance base, worked by the existing case loop, decided at the existing gate — archived like any intake and appended to the queue; the run record names them in `pm_cases`. The cycle opens on the obligation when the case is built, so the same due point can never surface twice, and a cycle case that a budget cut leaves unworked stays the obligation's open cycle: it rides the run's carry-over payload like any queued case and joins the next board that accepts it.
- **Only an outcome marks work performed.** `close_cycle` is called from `record_outcome` and nowhere else writes `last_performed_at` after approval: an accepted outcome stamps it from the outcome's own `recorded_at` and sets next due = performed + interval; a rejected outcome appends a deferral (reason = the outcome's work-performed note, previous due, rolled-to) and sets next due = deferral + the authored roll. The service refuses a rejected outcome with an empty note on a cycle case *before* the history write-back or any save — the same total-refusal discipline as the safety-stop confirmed fault — because a silent deferral is exactly the failure this layer exists to prevent. A cycle case dropped at carry-over acceptance rolls identically via `note_board_drop`, kind `board_drop`, so "not this shift" said at the turnover is never distinguishable from a deferral said at the gate.
- **Storage.** Proposals and obligations are `pm_records` (migration `0006`): one table, a `kind` column distinguishing them, JSONB payload, promoted machine/fault/status columns — the board-items/claims precedent, because a decision lands days after a draft and a due point weeks after an approval, so both must be findable by later requests rather than scanned out of other records' payloads.
- **Safety.** The PM layer evaluates on effective fault class; safety stops have no diagnosis and confirm no fault, so they draft nothing, and cycle cases are `maintenance_alert` — the machinery cannot produce, claim for, or alter a safety case. The golden pack's safety entries run unchanged against the same service with the PM hooks live.

Surfaces: `GET /api/pm/proposals`, `GET /api/pm/obligations`, `POST /api/pm/proposals/{id}/decision` (422 on a bad decision value or interval, 404 unknown, 409 on a second decision or a reasonless rejection), CLI `pm-proposals` / `pm-obligations` / `pm-decide`, the console's PM panel (pending proposals with rationale and decide controls; the obligations table), and the handoff's `pm` payload + PREVENTIVE MAINTENANCE text section (obligations with overdue flags against the handoff's own moment, pending proposals, every deferral with its reason and rolled date). The handoff `counts` dict is deliberately untouched.

## Endings: retirement and decommission (`lifecycle.py`)

Round 8's obligations were immortal by omission. Round 10 gives machines and obligations an end, computed in code and recorded like everything else — and keeps the ending strictly separate from the safety machinery: nothing here can close, decide, or soften a case on its own.

- **Retirement is a supervisor's act, and it is one-way.** `PmManager.retire_obligation` requires actor and reason (409 without either, 404 for an unknown or non-obligation id) and stamps the obligation: status `retired`, `retirement_kind: manual`, the reason verbatim. There is no un-retire path anywhere in the module — no method, endpoint, or flag reverses it. A pattern that returns starts over: its old evidence is watermarked (above), a fresh threshold drafts a fresh proposal, and approval creates a *new* obligation; the retired record remains as the memory of the old duty.
- **A retired obligation is inert, not deleted.** `due_cases` filters on `status == "standing"`, so no board ever surfaces its cycle again — the due point passing is a non-event. `close_cycle` and `note_board_drop` return a retired obligation unchanged: if its cycle case was kept open by a supervisor's disposition, that case's outcome lands on the case record alone and never stamps, rolls, or resurrects the obligation. The service's reasonless-deferral refusal likewise applies only to standing obligations — a kept case of a retired obligation is not deferring anything.
- **Decommission is one recorded act with computed consequences.** `MachineLifecycle.decommission` validates first (unknown machine 404; actor, reason, and a parseable `effective_at` required; a second act on the same machine refused — a machine is decommissioned once) and only then mutates: every *standing* obligation for the machine retires through the same `retire_obligation` path with `kind: machine_decommission`, the fixed reason `machine decommissioned`, and the new record's id as the link — manual retirements already on record are untouched, so the two endings never blur. The machine's open cases are snapshotted onto the record (`open_case_ids`): *open* is the board's unfinished business — `awaiting_supervisor`, or decided with the outcome still outstanding — never settled, dropped, or moot-closed history.
- **Disposition is per case, human, and recorded once.** `dispose` accepts only cases on that snapshot, only `keep` / `close_moot`, only with an actor, and only while the case is still open (a case that settled since the act is refused with its current state named). `keep` writes nothing but the disposition entry — the case is inherited, decided, and outcome-recorded exactly as any board case. `close_moot` stamps the case record (status `closed_moot`, a `closed_as_moot` block naming the decommission, mirroring `dropped_from_board`) and the service releases its standing claims via the allocation ledger, the way a gate rejection releases them. The disposition itself appends to the machine record; a second disposition for the same case is refused.
- **Intake closes at the entry points, and only there.** The service's `_refuse_if_decommissioned` guard runs at the head of `run_case` and over `run_board`'s submitted cases — the two places new work enters — raising a `ValueError` that names the state, the decommission record, its effective moment, actor, and reason (409 over HTTP). Nothing else consults it: carried-over settlements read stored records, PM due cases come from obligations (already retired), and kept cases stay workable. A decommission therefore cannot strand work already on the board — it can only refuse work that has not started.
- **Safety is untouched, structurally.** The lifecycle layer never reads or writes a case's exit, gaps, or safety state. A safety case on the machine is listed like any open case — listing is not disposing — and remains `awaiting_supervisor` with its `safety_stop` intact until a supervisor dispositions it (keep) or closes it as moot by the explicit choice; the decommission act itself changes nothing about it. History entries and confirmed faults for the machine are never modified: the past stays fully readable.
- **Storage.** Machine state is a stored record, not plant-model data: `kb.json` is authored and immutable (a test pins its integrity), so the lifecycle gets its own table (migration `0007_machine_records.sql`) on the 0006 precedent — one row per machine, ever, keyed by machine with the full record as JSONB; the intake guard, the PM layer's decommission check, and the surfaces all read the state from the store. Obligation retirement needs no migration: the fields ride the obligation's existing JSONB payload with defaults, so pre-round payloads validate unchanged.

Surfaces: `POST /api/pm/obligations/{id}/retire`, `GET /api/machines`, `POST /api/machines/{id}/decommission`, `POST /api/machines/{id}/dispositions` (422 on a bad disposition value, 404 unknown machine, 409 on validation refusals), CLI `pm-retire` / `machines` / `machine-decommission` / `machine-dispose` (and `pm-obligations` now prints retired obligations with their reasons), the console's PM panel (status column + retire control) and machines panel (state, decommission control, per-case disposition controls), and the handoff's `pm.retired` list + PREVENTIVE MAINTENANCE text lines (standing obligations stay in `pm.obligations`; the `counts` dict is again untouched).

## The board looks ahead: the parts outlook (`outlook.py`)

The allocation ledger is present-tense: who holds what, now. Round 11 adds the forward-looking read the plant's records already support — projected demand against the shelf over a stated horizon — and it is built as a pure projection over the same records, with the discipline that a number a supervisor cannot trace is a guess the system should not print.

- **Three sources, all of them record facts.** Standing claims (`status == "claimed"`) are demand the board has already committed. Open case records (`awaiting_supervisor` / `approved` — rejected, dropped and moot-closed cases are finished business) contribute their plan requirements' unsatisfied remainders. Standing PM obligations contribute their **next due cycle only**, quantified by `kb.sop_for(machine_id, fault_class).required_parts` — the SOP that cycle case will itself run — when the due point falls inside the horizon (overdue cycles count: their parts are needed now). Each source lands as a dated `PartDemandLine` naming its source record (case id, claim's case, obligation id); the report's `basis` string states the method on its face.
- **One count per unit.** A satisfied requirement whose case holds a standing claim for the drawn part is the claim, not a second demand. A satisfied-but-unclaimed requirement projects onto the part the plan runs on — the substitute, when the plan uses one (the ledger's own accounting, `claim_from_record`, agrees). An obligation with an open cycle (`cycle_case_id` set) projects through that case's record alone. The parts pass reads final `CaseResult.plan` records, so it sees requirements exactly as verify left them.
- **The biting moment is computed.** The supply line is the plant model's authored `qty_on_hand` (`kb.part_qty`) — stock was already quantified in the KB, so the round adds no inventory model; an unstocked part has supply 0 and any demand on it is a shortage. The walk orders the demand: everything already on the books (claims, case demand, overdue cycles) is effective at the projection moment and alone can make a part *already short*; otherwise the future PM lines, in due order, tip it at the first due date that pushes cumulative demand past the shelf, and the row names the obligation that did it. `shortfall > 0` is the only risk test — exactly zero is covered.
- **What cannot be quantified is stated, not invented.** An obligation whose machine + fault class has no SOP on record lands in `unquantified_pm` with the reason; an SOP that names no parts was consulted and contributes zero. Retired obligations are skipped entirely — the projection reads the same `status` the lifecycle layer writes, so a retired duty's due cycle is simply not in the book. No storage is added, and no migration: claims, case records and PM records already persist everything the projection reads.
- **A pure read model.** `build_outlook(store, now, horizon_days)` touches nothing; the golden pack pins the store's case, claim and PM records byte-identical across a build, and the tests pin the same for the service path. The outlook creates no cases, places no claims and orders nothing — procurement is deliberately out of scope: the agent's parts machinery has always stopped at the planning reservation, and the projection stops at advice.

Surfaces: `GET /api/parts/outlook?horizon_days=` (422 below 1), CLI `outlook` (`--horizon-days`), the console's outlook panel under the board (shortage banners with their traced lines, the covered-demand table, unquantified notes), the demo's `[OUTLOOK]` section, and the handoff's `parts_outlook` payload + COMING PARTS SHORTAGES text section — computed at the handoff's own moment over the authored horizon, so the incoming shift reads the same shortages the API would serve; the `counts` dict is again untouched.

## What the plant doesn't know: the knowledge-gap report (`gaps.py`)

The outlook names a missing SOP when it stops a PM cycle's parts from being priced. Round 12 names the same absence where it costs the most: in the case loop. A case whose diagnosed fault has no SOP for its machine cannot converge on the plant's own procedure — offline it exhausts at `unknown_fault` (the diagnosis derives hypotheses from SOPs, so there is nothing to name and no evidence to cite), and the verify stage's safety check, which reads the SOP's mandatory steps, has nothing to check. Each case was escalated honestly; the *pattern* — the same hole blocking repeatedly — was computed nowhere. The gap report is that computation, a pure read model in the outlook's mould.

- **One membership rule, from the records.** A stored case record contributes when it carries a diagnosis, its top fault class fails `kb.sop_for(machine_id, fault_class)` — the loop's own test, and the outlook's `unquantified_pm` test, referenced rather than forked — and it ended without a verified plan (exit neither `converged` nor `safety_stop`; safety stops are excluded because they end by rule, diagnosis or none, and an SOP would not have changed them). Rows group by the missing asset, (machine, fault): blocked count, case ids in record chronology (created, then case id — the stats module's ordering), earliest/latest, summed loop rounds as the gap's price, the exit mix, and the still-awaiting case ids as the *open now* signal. Ranking is open-now first, then blocked count, then rounds burned, then the asset name — a total order over the rows, deterministic by construction. Standing PM obligations failing the same test annotate their pair's row (`standing_obligation_ids`); retired obligations annotate nothing.
- **The advisory boundary is structural.** The report exists to advise the KB maintainer, and its schema is the enforcement: `KnowledgeGap` carries identifiers, counts and timestamps only, and a test pins the exact field set — there is no text, step or content field a drafted procedure could ride in. The system never authors SOP content: no draft procedures, no suggested safety steps, no proposed parts lists. The maintainer authors the SOP into the plant model (`data/kb.json`, an authored edit kept honest by the KB shape test — registered machine, mandatory safety steps present), and blocked cases then move only through the pre-existing flows: a gate decision, or a fresh run whose record upserts the old one. A gap therefore *stops biting* observably — its row stops growing, and disappears once every contributing record has been superseded by a converged re-run — without any record ever being rewritten to look healed.
- **Surveyed and excluded, deliberately.** Three candidate categories did not survive the survey, and the exclusions are part of the design: an SOP naming no parts cannot block a case (its plan needs nothing) and is a consulted fact in the outlook, not a hole; machine criticality does not exist to be missing (criticality is a line attribute; every line carries one; unknown lines default silently in priority); and a part absent from the inventory register is indistinguishable on the record from a planner inventing a part — the golden pack's defect case G22 is exactly that — so parts blocks stay in the handoff's outside-world family rather than being re-attributed to the plant's knowledge. A rival fault without an SOP is likewise not counted: an unseparated pair's block is jointly caused, and the record cannot charge it to one procedure.
- **No storage, no migration.** Case records and PM records already persist everything the report reads; like the outlook, it is computed on demand from the store and the plant model, and the golden pack pins the store byte-identical across a build (a unit test also pins zero reasoner calls across two service-level builds — the report has no reasoner handle at all).

Surfaces: `GET /api/knowledge/gaps`, CLI `gaps`, the console's gaps panel under the board (open gaps as red banners, history as amber), the demo's `[GAPS]` section, and the handoff's `knowledge_gaps` payload + KNOWLEDGE GAPS text section — computed at the handoff's own moment; the `counts` dict is again untouched.

## The supervisor edits, the machine re-checks: amendments (`amendments.py`)

The gate's decision vocabulary was approve / reject, and both are coarse: approval accepts the plan exactly as the loop proposed it, rejection discards work that may be one part away from right. Round 13 adds the third path the floor actually uses — the supervisor amends the plan — and builds it so the amendment inherits the loop's discipline instead of bypassing it.

- **Overlay, never edit.** A `PlanAmendment` appends to the case record (the `case_records` payload — no migration; the record already carries the decision, the drop stamp and the moot stamp the same way). It names its kind, its supervisor and its reason; anonymous and reasonless amendments are refused at recording, as are amendments on a case not awaiting its decision and on a safety stop (which has no plan — its refusal says so). The loop's `plan` on the record is never mutated: `apply_passing_amendments` derives the gate's current plan by replaying the *passing* amendments over a deep copy, and every surface that prints a plan — packet, console, API (`effective_plan` beside the original), outlook — prints the derived one, with the swap marked in the step text and the amendment trail printed alongside. A carried case inherits its record standing at the turnover, so its amendments and their verdicts carry with it by construction (pinned in the tests).
- **Re-verification is the verify stage, minus the model.** Recording builds the candidate plan (current effective plan + the tentative amendment), re-measures every requirement against the shelf net of *other* cases' claims (`AllocationLedger.effective_qty_excluding` — the case's own claims are the plan being measured, not contention; the substitute search does **not** run, because the supervisor's swap is the proposal under test, not an invitation for the machine to choose a different one), and runs `guardrails.verify_plan` over it, plus `substitution.constraint_violations` for a swap's slot. The verdict (passed / failed, with the Gap list verbatim) is stamped on the amendment before it lands. The approve path in `service.record_decision` reads the *latest* amendment's verdict before either of its two decision paths (graph resume or direct record write) — a stale approve of a failed-amendment case is refused by name, and the resume path merges the store-side amendments onto the resumed record so a checkpointed decision cannot lose them.
- **The vocabulary's edges are refusals, not conventions.** A swap's target must be on the parts register (`kb.part_qty` non-None) — free text is refused because nothing downstream could verify it. Its compatibility paperwork (`_swap_paperwork`) has exactly three honest shapes: the KB-listed pairing (authored basis + deltas, the substitution record's own data), the slot's own part (a swap back), and the supervisor-specified pairing — labelled unlisted on its face, deltas computed from the two spec sheets, compatibility judged on the SOP's constraints and the shelf with the named supervisor carrying the pairing. A strike's target must exist in the current plan and must not be a mandatory safety step — tested by the step's own `mandatory` flag and by the guardrails' suffix match against `kb.mandatory_safety_steps(sop)` — and the refusal names the step and its SOP. Step *addition* is not a missing feature but a refused category, for the reason stated in the module: an added step has no diagnosis behind it.
- **Claims move only behind a passed verdict.** On a passing swap the service releases the old drawn part's claim (`released_by_amendment`, by the amending supervisor) and claims the new part under the run that held the old claim (`AllocationLedger.claim_part`, the ledger's one-row revive-or-create discipline) — in the same call that persists the amendment. On a failure, the ledger is untouched (the golden pack pins it), so the case's AMENDMENT_FAILED face never coexists with a half-moved allocation. The handoff's AMENDED AT THE GATE section and the stats' `amendments` block (recorded / passed / failed / approved-after-amendment counts, deliberately separate from the outcome vocabulary's `accepted_with_changes`, which describes what the floor did with a plan, not what the gate did to it) are projections over the same records.

## After the gate: outcomes, live accuracy, the watch

The gate decision (approve/reject) is not the end of the record's life — it is the start of its evidence. Round 2 closes the loop:

- **Outcomes** (`POST /api/cases/{id}/outcome`, `SupervisorOutcome` on the record): the supervisor records the plan's disposition (`accepted` / `accepted_with_changes` / `rejected` — a separate axis from the gate decision: whether the *drafted plan* was the plan that got executed), the confirmed fault, work performed, actual downtime, parts used, resolved. Validation happens at the transport (decision enum; confirmed fault must be in the KB vocabulary, `kb.fault_classes()`; non-negative downtime), because the outcome is ground truth for everything below. An outcome is recorded once; a second is a 409, not an edit. It rides inside the case record's JSONB payload — no new table, and the record on file remains exactly the record on file.
- **The learning loop** (`history.py`): a confirmed fault does not stay trapped in the record that earned it — it is written back to the machine's history as a `HistoryEntry`, where future diagnoses read it. The seam follows the repo's storage idiom: the packaged KB is authored, versioned ground truth and is never appended to at runtime, so confirmations — runtime state — get their own store table (migration `0004`, JSONB payload like board items), keyed `hist-<case_id>` so the once-per-case outcome makes the write idempotent by construction. Only a confirmed fault writes, under any disposition (a rejected plan with a confirmed fault still teaches the fault; an outcome confirming nothing writes nothing). A safety stop refuses a confirmed fault in code, computed *before* the outcome persists, so the refusal is total — no outcome on the record, no entry in memory — because a safety case has no diagnosis to confirm. The diagnoser reads one merged view (confirmed first, sources marked): the offline signals cite the first matching entry through the same evidence path as always — now a confirmation is cited as the floor's own finding — and, on a focused loop-back, a supervisor-confirmed precedent for the leading fault separates a rival the readings could not (the same re-score a readings discriminator performs; recorded history never separates). The stats payload gains a `learning_loop` section — write-back counts by machine, and repeat-fault top-1 (scored cases whose machine + fault an earlier case's outcome had already confirmed) beside the overall top-1, both plain, with an explicit note when there are no repeats yet — and the handoff names the confirmed faults the next shift inherits.
- **Live diagnosis accuracy** (`stats.py`, `GET /api/stats/diagnosis`): a pure aggregation over records — the same code path serves both stores. A record enters fault scoring only when a fault was confirmed *and* the loop produced hypotheses (a record carrying a confirmed fault but no hypotheses is counted separately as `confirmed_without_diagnosis`, never silently dropped). Metrics: top-1/top-2 accuracy, per-class precision/recall with counts, mean rounds over confirmed convergences, plan-acceptance counts/shares, downtime error (signed mean = bias, MAE = accuracy), and the learning-loop section above. With zero outcomes the payload is `available: false` with an explanatory note — honest empty states over flattering zeroes.
- **Shift handoff** (`handoff.py`, `GET /api/board/handoff`, `?format=text` for plain text): composed entirely in code from the current records — awaiting cases in board order, escalations with open gaps, blocked-external cases with their unsatisfied parts, safety stops, open reliability items, the supervisor-confirmed faults written back to machine history, and the latest board run with its budget-cut remainder. The JSON and the text are rendered from the same dict, so the shift-log paste cannot drift from the API. No model writes any part of it: a handoff is a safety-adjacent document, and an invented gap (or a dropped safety stop) is worse than a terse one.
- **Recurring-fault watch** (`reliability.py`, `ReliabilityPolicy` in `loops.py`): invoked from the service wherever a case reaches the gate (`_persist_case`, used by both the single-case path and the board graph's result callback) and again on outcome recording. The fault a case counts as is its *effective* class — confirmed when an outcome carries one, else the top diagnosis — so a confirmation can complete a pattern or dissolve one. Counting is a rolling window over record timestamps anchored at the check moment; at the threshold (default 3 in 14 days) the watch persists one `reliability_review` `BoardItem` (its own table, migration `0003` — an item is not a case and has no loop record) with the contributing case ids as evidence, deduplicated on (machine, fault class) while an item is open. The item is the entire action *of the watch*: it appears on the board and in the handoff, and triggers nothing automatic itself. What the pattern earns beyond the item — the PM proposal drafted from this same contributing set — is the pm.py layer above.

## Guardrails as code

| Guardrail | Where | Effect |
|---|---|---|
| Evidence required | critique contract + code gap `unevidenced_hypothesis` | a hypothesis with empty evidence can never converge |
| Mandatory safety steps | `guardrails.verify_plan` vs the SOP's code-side list (matched by step id or ≥0.55 token overlap, so rewording can't smuggle one out) | missing step = blocking safety gap |
| Banned actions | `screening.screen_plan_step` over every plan step (interlock/guard bypass, defeating a safety device, hot work on live equipment) | safety gap → `safety_stop` the same round |
| Injection screen | `screening.screen_text` on title/description/notes before anything else: instruction-shaped spans (incl. "skip the lockout…") are struck, flagged on the record, and the surviving text is fenced as untrusted data in prompts | planted instructions never reach a plan |
| Parts reality | verify-stage parts pass: shelf truth for every requirement + the KB substitute search with SOP constraints (`substitution.py`), then the `part_unavailable` gap + blocked-exit rule | a plan can only promise what the shelf holds — directly, or via a substitute that was searched, checked and recorded |
| One shelf per board | allocation ledger (`allocation.py`): converged plans claim their drawn parts; every measurement reads the shelf net of standing claims | two cases on one board can no longer both plan around the same last unit — the loser blocks with the claiming case named, and a gate rejection releases the claim for future runs |
| Draft language | `guardrails.draft_language_ok` | no performed-work claims in drafts |

## Backends behind the port

`backends.get_reasoner` selects by `REASONING_BACKEND`. All model-backed reasoners share `StructuredReasoner` (prompts, schema validation, one bounded retry, usage/latency accounting, translated provider errors — a dead provider fails the run loudly and is written to the error log; nothing is ever silently re-routed to another backend):

- **`MuseSparkReasoner`** (`muse`): Muse Spark 1.3 via the OpenAI SDK against `https://api.meta.ai/v1` (Chat Completions). Refuses at construction without `MODEL_API_KEY`.
- **`MuseResponsesReasoner`** (`muse` + `MODEL_SURFACE=responses`): the Responses surface with `include=["reasoning.encrypted_content"]`. The per-case `session` dict on `CaseContext` accumulates reasoning items across rounds; each call replays them ahead of the new prompt. Without this, a multi-round loop restarts the model's reasoning every round — the continuity is the reason the surface exists in this blueprint.
- **`LLMReasoner`** (`llm` / provider aliases): Anthropic Messages, or any OpenAI-compatible endpoint (which includes NVIDIA NIM, hosted or self-hosted, via `OPENAI_BASE_URL`), or Ollama.
- **`OfflineReasoner`** (`offline`, default): deterministic SOP-threshold rules with a small signal function per fault class, discriminating checks for focused rivals, keyword fallback, and an honest `unknown_fault` when nothing matches — which the loop then escalates as `exhausted` rather than dressing up. It exists so tests/evals are hermetic; it is labelled a plumbing backend everywhere it appears.

Cost estimation uses a small price table (`backends._PRICE_PER_MTOK`): Muse Spark standard tier $1.25/M in · $4.25/M out (contributor tier priced separately); unknown models report no estimate rather than a guessed one.

## The reasoner regression gate (`regression.py`)

A backend behind the port is a promise, not a proof: the same loop behaves differently under a different model, a different Muse Spark point release, or the same model on the other surface (reasoning continuity changes what round 2 concludes). The gate exists so a swap is *measured* before it is trusted.

- **Harness.** `run_suite` drives a fixed suite — the golden pack's 20 `case` entries, loaded from `evals/golden.jsonl` so the two packs can never drift apart — through one named configuration, each case on a fresh service exactly as the golden pack runs it. A `CountingReasoner` wraps the reasoner at the port (payloads pass through untouched) to count model calls; the record per case carries exit, rounds, top diagnosis, tokens, and two **safety pins**: `safety_zero_calls` (stated for safety-observation cases) and `mandatory_steps_covered`, computed with `guardrails.verify_plan`'s own step-matching so the pin reads a plan exactly as the loop's verify round judged it. The configuration stamp is backend + model + **surface**: `muse` (chat) and `muse-responses` are different configurations at the same model name, because continuity is a behavioural difference.
- **Comparison.** `compare_runs` is a pure function of two records. Criteria are authored in `GATE_CRITERIA` / `EXIT_SEVERITY` and evaluated in a fixed order — suite completeness, then safety pins, then exit regressions, then diagnosis agreement (floor 0.90). The order is the design: pins are absolute and evaluated before any aggregate, so a candidate cannot average its way past a safety case that got reasoned on; a converged plan missing a mandatory step fails even at 100% diagnosis agreement. The severity order (`converged > blocked_external > budget_exceeded > exhausted > safety_stop`) ranks exits by how much verified work the plant keeps; ranking `safety_stop` last is deliberate — as a *regression* it means the candidate refused work the baseline did, while the dangerous direction (reasoning on a safety case) is a pin, never a severity judgement. Improvements and round/call deltas are reported in the same diff, ungated.
- **The baseline and the stub.** The offline record is committed (`evals/gate/baseline-offline.json`) and served at `/evals/gate-baseline`; regenerating it is the deliberate, visible act of moving the reference. The shipped stub candidate (`stubs.py`) — one diagnosis difference (G14), one extra round (G20), PASS at 95% — is the gate's exercise partner and is *not* registered in `get_reasoner`: no configuration value can select it. Pin-breaking candidates exist only in `tests/test_regression_gate.py`, in two forms that pin the division of labour: tampered records (the unit `compare_runs` actually judges) and a through-the-loop safety-stripping planner, whose record shows incomplete plans on *non-converged* cases — the verify round held them, so the gate fails that candidate on exit regressions, not pins. The golden pack's RG1 entry runs the whole comparison end to end so a gate regression fails the golden gate too.

## Persistence & topology

- **Store port** → `PostgresStore` (records, board runs, board items, history entries, part claims, PM records, error log as JSONB rows) or `InMemoryStore` (test double). Board/metrics/stats/handoff read models are computed from records in both.
- **Checkpointer**: Postgres saver when `DATABASE_URL` is set, in-memory saver otherwise, `CHECKPOINTS=off` to disable (gate decisions then always take the direct-apply path).
- **Vector index** for KB retrieval: pgvector table (`migrations/0002`), dimension-free column so embedder swaps don't migrate; in-memory cosine index as the double. Embedder: hashing (offline) or a provider `/embeddings` endpoint.
- **Object store**: raw case payloads archived to S3 (compact stdlib SigV4 client — the blueprint's only outbound storage call) or memory.
- **Migrations**: numbered SQL in `migrations/`, applied in order on first Postgres connection by store and index alike, recorded in `schema_migrations`; `MIGRATIONS_DIR` overrides the location (the Docker image ships them at `/app/migrations`).
- **API**: FastAPI, JSON logs with request IDs, `/health` + `/readiness` (503 when Postgres is configured but unreachable; explicit test-double labelling otherwise), optional `API_KEY` gate on non-probe routes. The console is one static HTML file with no dependencies.

## Testing the loops themselves

The eval pack and suite are designed around the loop semantics, not just outputs: scripted-critique controller tests isolate exit logic from any reasoner; defect planners (drop-safety / wrong-part / banned-step) prove the verify round catches realistic component failures; board evals pin the priority order and both budget cuts; the learning entries run a case, record the outcome, and re-run a similar case against the same store, so the write-back is the only variable; the allocation entries run two cases at the shelf's only belt — contention, the named claim, the gate release, and a fresh run converging — against the same store for the same reason; the carryover entries run a whole contention board across two shifts against the same store — the turnover is the only variable between the blocked case staying blocked and it converging on the freed belt; the pm entries run the whole preventive-maintenance story against one store — threshold, proposal, edited approval, board surfacing, outcome, next due — plus the watermark and the below-threshold silence, so a regression in any link of that chain fails a named step; the Muse adapter tests pin the wire shape and the reasoning-continuity round-trip against stubbed transports, which is the strongest claim available before a live key exists. The regression-gate tests pin the comparison itself: determinism against the committed baseline record, the stub candidate's PASS, and each FAIL path (pin violations, exit regressions, the agreement floor, a short suite) — with the breaking candidates constructed in the tests, never shipped.
